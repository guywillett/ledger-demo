# Slice 2 — Transactional outbox and withdrawals

Status: done (Node.js / TypeScript); every item under *Done when* is met, except the tag, which follows the review and merge
Implementation: Node.js / TypeScript (Go to follow in a later slice)
Builds on: [slice 1](slice-1-incoming-payments.md). Its conventions, decisions and vocabulary hold unless this spec says otherwise.

**Scope principle:** this is a demonstration, so each pattern is shown once. Where a production system would repeat a pattern this slice leaves out (a compliance review, an extra event hop), the spec says so and why, rather than building it a second time.

## Goal

Two things slice 1 could not do:

1. **Never lose an event.** Replace publish-after-commit with a **transactional outbox**: every event is stored in the same transaction as the state change it announces, and a relay publishes it. Closes the commit-then-publish gap (stranded money) for good.
2. **Send money out, exactly once.** Client-initiated **withdrawals** with an `Idempotency-Key`, funds held while the transfer is in flight, an outgoing call to a provider that can time out with an unknown outcome, and the provider's asynchronous result coming back by webhook. Whatever is repeated, retried, raced or crashed, each withdrawal debits the account at most once, and the funds are either executed or released, never both and never neither.

`v0.1-simple-ledger` is tagged when this slice is merged (slice 1 decision 2).

## Part A — Transactional outbox

### The problem it closes

Slice 1 commits the payment, then publishes `payment.created`. A crash in between leaves the payment `created` forever (stranded money), narrowed only by provider retries re-announcing it. Publishing *before* commit is worse (an event for a payment that may roll back). The two writes can't be made atomic across Postgres and NATS, so make them one write: store the event in Postgres with the state change, and publish it from there.

### `outbox`

| Column | Type | Notes |
|---|---|---|
| id | uuid PK | UUIDv7, no default (always generated by the application, like every event ID); **is the event's `event_id`**, so an event keeps one ID however often it is published |
| entity_type | text | what the event is about: `payment` (`withdrawal` added with Part B); mirrors `balance_movements.reference_type` |
| entity_id | uuid | UUIDv7 of that entity. Indexed with `entity_type`, so reconciliation joins outbox rows to payments without parsing TypeIDs out of the payload |
| subject | text | e.g. `payment.created`, `withdrawal.held` |
| msg_id | text | `Nats-Msg-Id`, `<entity TypeID>.<status>` as in slice 1 decision 20; `UNIQUE`: an entity enters a status once, so one event per entity and status (a backstop: the conditional transitions already guarantee it) |
| payload | jsonb | the event as published (the wire format, built by the same TypeScript builders as before). `jsonb` keeps the content, not the text: the relay re-serialises it, so key order may differ from the builder's; consumers and the contract tests don't depend on key order |
| created_at | timestamptz | |
| claimed_until | timestamptz null | relay lease (below) |
| attempts | int | publish attempts, for alerting on a stuck event |
| last_error | text null | |
| published_at | timestamptz null | set once the stream has acknowledged it |

Partial index on `(id) WHERE published_at IS NULL`: the relay's query stays fast however many published rows accumulate.

### Writers

Whoever makes a state change that has an event inserts the outbox row **in the same transaction**. A data-access function that writes an event therefore takes a `Tx`, per the transactions convention. For `payment.created`, `recordNotification` becomes two statements in one transaction (the existing upsert, then the outbox insert when a payment was created); the payload is built in TypeScript by the existing event builder, so there is one definition of the event's shape, checked against `contracts/events/`.

Consequences for slice 1's `POST /payments`: the request no longer publishes, so the `503`, the re-publish on duplicate and the "new `event_id` per re-publish" caveat all go (decisions 18 and 20's logging detail are superseded). A duplicate is just a duplicate.

### Relay

A new process (`node/src/relay/`, compose service `relay`, same image), several instances allowed:

1. **Claim** a batch in one statement (its own short transaction): `UPDATE outbox SET claimed_until = now() + lease, attempts = attempts + 1 WHERE id IN (SELECT id FROM outbox WHERE published_at IS NULL AND (claimed_until IS NULL OR claimed_until < now()) ORDER BY id LIMIT $n FOR UPDATE SKIP LOCKED) RETURNING …`. `SKIP LOCKED` lets instances claim disjoint batches without waiting on each other.
2. **Publish** each claimed event in `id` order, outside any transaction (convention: never wait on the network inside one), with its `msg_id`, waiting for the stream's acknowledgement.
3. **Mark** each acknowledged event: `UPDATE outbox SET published_at = now(), claimed_until = NULL, last_error = NULL WHERE id = $1 AND published_at IS NULL`. A failed publish records `last_error` and moves the lease to `now()` + a retry delay (1 s after the first attempt, doubling per attempt, at most 60 s), so the event backs off instead of being reclaimed at once; the rest of the batch carries on. A batch in which nothing could be published (e.g. NATS down) makes the relay back off before claiming more. Both are conditional, so a relay whose lease ran out and whose event another relay has since published changes nothing (`skipped`).

**Batch and lease:** `RELAY_BATCH_SIZE` (default 10) and `RELAY_LEASE_MS` (default 30 s). The lease must outlast a batch's worst case, every publish timing out in turn (batch size × the 2 s publish timeout = 20 s), plus a 5 s margin for the database work in between, or another relay would reclaim events still being published; the relay refuses to start otherwise. The lease is also how long a crashed relay holds back the events it claimed, so it stays short and the batch size gives way: a healthy publish is acknowledged in about a millisecond, and a full batch is followed by the next one at once. It is capped at 60 s: a crashed relay's events are published again when its lease expires, and the stream drops that repeat only within its 120 s `duplicate_window`.

**Polling:** a full batch means there may be more, so the next one runs at once. Otherwise the relay waits 200 ms, doubling while batches keep coming back empty, up to 1 s. `LISTEN/NOTIFY` to wake the relay at once is a later optimisation. A failed batch (e.g. the database is down) is logged and retried with backoff; on shutdown the batch in progress is finished first.

**Delivery guarantee: at least once.** A relay that crashes after publishing but before marking leaves the lease to expire, and the event is published again: within the stream's duplicate window the `msg_id` makes the stream drop it; beyond it, consumers are idempotent on state (they already are). **Order:** one relay publishes a batch in `id` order, but nothing orders events across instances or retries; consumers must not depend on order (they don't: every step is a conditional transition).

The API no longer connects to NATS at all; the relay is the only publisher.

## Part B — Withdrawals

### Data model

**`account_balances`** gains `held bigint NOT NULL DEFAULT 0 CHECK (held >= 0)`: funds reserved for withdrawals in flight. `move()`'s `Bucket` becomes `external | pending_in | available | held`, with the same fixed-statement update (one more column) and the CHECK reported as an `OverdraftError` naming the bucket.

**`withdrawals`**

| Column | Type | Notes |
|---|---|---|
| id | uuid PK | TypeID prefix `wd` |
| account_id | uuid FK | |
| idempotency_key | text | the client's `Idempotency-Key`, 1–255 characters; `UNIQUE (account_id, idempotency_key)` |
| amount_minor | bigint | `CHECK (amount_minor > 0)` |
| currency | text | `CHECK (currency = 'EUR')` |
| creditor_iban | text | destination, normalised, format CHECK as elsewhere |
| creditor_name | text | required by SEPA; 1–70 characters (the SEPA Credit Transfer limit), from the SEPA basic character set (decision 32), not only spaces |
| remittance_info | text null | the payment reference shown to the recipient; 1–140 characters (SEPA unstructured remittance information), from the SEPA basic character set; none is `NULL`, never `''`, so a repeat compares equal |
| status | text | `held`, `submitted`, `executed`, `failed` |
| failure_reason | text null | set exactly when `failed`: `CHECK ((status = 'failed') = (failure_reason IS NOT NULL))` |
| provider_transfer_id | text null | the provider's ID, once known |
| created_at / updated_at | timestamptz | |

`withdrawal_status_history`: as `payment_status_history` (append-only, triggers).

**`balance_movements`**: `reference_type` adds `withdrawal`; `reference_step` adds `hold`, `execute`, `release`. The two are checked as a pair (one CHECK replaces the per-column ones): `payment` with `book | credit | return`, `withdrawal` with `hold | execute | release`. `move()`'s `Movement` type mirrors the pairing as a discriminated union, so a payment reference with a withdrawal step is a compile error. Same unique reference, so every withdrawal movement is applied at most once whatever the caller does. `outbox.entity_type` also allows `withdrawal`.

Schema changes are **new migrations**: slice 1 is merged, so its migrations are no longer edited.

### State machine

```text
(insufficient funds: nothing stored, 422)

held ──► submitted ──► executed
  │          └───────► failed
  ├──────────────────► executed   (provider's update arrived before our submit response)
  └──────────────────► failed     (provider refused the submission, or its update arrived first)
```

| Transition | Movement | `reference_step` | Owner |
|---|---|---|---|
| (create) → held | `available` → `held` | `hold` | API request (decision 25) |
| held → submitted | none: the provider has accepted the instruction | — | submitter |
| held \| submitted → executed | `held` → external | `execute` | transfer-update webhook (stores the update's transfer ID if none was recorded at submission; an ID that differs from the stored one is a contradiction: `TransferIdMismatchError`, nothing changes) |
| held \| submitted → failed | `held` → `available` (released) | `release` | submitter (permanent refusal) or webhook |

**Why `held → executed` and `held → failed` exist:** the provider may send its result before the submitter has processed the response to its own request (the provider accepts, fires the webhook, then our HTTP response arrives, or our process crashed in between). The webhook must not wait for, or depend on, the submitter's bookkeeping. Whichever conditional transition commits first wins; the other finds the withdrawal already past `held` and skips. `executed` and `failed` are final, and a final status never changes (an update contradicting one is a conflict, below).

`executed` means the money has left: the provider has executed the SEPA transfer. A return after that is a new flow (*Out of scope*).

Event naming as slice 1: `withdrawal.<new status>`. Only `withdrawal.held` is published in this slice (the submitter consumes it); the others are added when something consumes them.

**`withdrawal.held` v1** (`contracts/events/withdrawal.held.v1.json`, Zod in `shared/events.ts`): `event_id`, `event_type`, `schema_version`, `withdrawal_id`, `account_id`, `amount_minor`, `currency`, `occurred_at`; `Nats-Msg-Id` `<withdrawal TypeID>.held`. **No destination IBAN, creditor name or remittance text:** those are personal data, and the stream keeps messages for 7 days, beyond our control once replicated. Consumers read the details from the database by `withdrawal_id`. This follows slice 1's rule that events carry our IDs only.

**Stream `WITHDRAWALS`** (`nats/streams/WITHDRAWALS.json`): subjects `withdrawal.>`, the same settings as `PAYMENTS` (file storage, limits retention, 7 days, 2-minute duplicate window). The relay maps each subject to its stream (`streamForSubject` in `shared/nats.ts`: `payment.*` → `PAYMENTS`, `withdrawal.*` → `WITHDRAWALS`; an unknown subject is recorded as a publish failure), publishes with `expect: { streamName }` so a subject landing in another stream or none fails loudly, and checks both streams exist at startup. The outbox's `entityType` / `entityId` are a discriminated union (`payment` with a payment ID, `withdrawal` with a withdrawal ID).

### `POST /accounts/:account_id/withdrawals`

Client-initiated. Header `Idempotency-Key` (required; 1–255 characters from `[A-Za-z0-9._:-]`, e.g. a UUID the client generates per intended withdrawal). Body: `{ amount_minor, currency: "EUR", creditor_iban, creditor_name, remittance_info? }` (amounts as digit strings, IBAN through `parseIban`, as slice 1). The body is **strict**: unknown fields are a `400` (decision 33). `creditor_name` and `remittance_info` are trimmed and checked against the SEPA basic set (decision 32); `remittance_info` absent, `null`, `""` or blank means none (`null`).

One transaction (`requestWithdrawal()`, `withdrawals/requests.ts`; the route only maps its result to a response). Steps 1 and 2 are one function, `createWithdrawal()` (`ledger/withdrawals.ts`), the only way to create a withdrawal: a `held` withdrawal without its hold would let settling it spend other withdrawals' reserved funds (`held` is one bucket per account).

1. Insert the withdrawal (`held`) and its history row: `INSERT … ON CONFLICT (account_id, idempotency_key) DO NOTHING RETURNING …`.
2. If inserted: `hold()`: `move(available → held, step hold)`. On insufficient funds, `hold()` translates the `OverdraftError` on `available` into a thrown `InsufficientFundsError` (a business outcome, kept distinct from `OverdraftError`, which the worker treats as a bug). It throws rather than returning a result because Postgres aborts the transaction after the failed statement: the whole transaction rolls back, nothing is stored, and the API catches the error outside the transaction and answers `422` with problem type `insufficient-funds`.
3. If inserted: the outbox row for `withdrawal.held`.
4. If not inserted (the key exists): compare the stored withdrawal's details with the request (`amount_minor`, `currency`, `creditor_iban`, `creditor_name`, `remittance_info`), directly, as slice 1 decision 16: same → `200` with the withdrawal **in its current status**; different → `409` with `differing_fields`. The read only classifies; the insert already decided.

An unknown account is found by the insert's foreign key, not by a read first: `insertWithdrawal` translates the `foreign_key_violation` into an `AccountNotFoundError`, thrown like `InsufficientFundsError` (the failed statement has aborted the transaction) and answered `404` after the rollback.

Responses: `201` created (status `held`), with `Location: /withdrawals/<id>`; `200` repeat; `400` invalid body, IBAN or key (every problem listed at once); `404` no such account; `409` key reused with other details (`differing_fields`, names only); `422` insufficient funds. The response is the withdrawal without `provider_transfer_id`: provider identifiers stay at the edge.

**The insufficient-funds check is the database's**, not a read: the `CHECK (available >= 0)` rejects the `move()` atomically, so two concurrent withdrawals that together exceed the balance can never both succeed (no check-then-act). Concurrent requests with the *same* key: `ON CONFLICT` makes one insert and the others wait for it, then see a repeat (or, if it rolled back for insufficient funds, each tries afresh).

What the key does and doesn't do:
- It makes **retrying a request** safe: a client that timed out can resend the same request and gets the same withdrawal, never a second one.
- **Only a successful request consumes a key.** The key is a unique column on the withdrawal row, so it is taken only when a withdrawal commits. Every failure rolls back and leaves the key free for a retry: invalid input (`400`), insufficient funds (`422`), and above all our own failures (`500`, the database unavailable, a crash mid-request). Nothing is cached, so a transient fault can never be replayed as a permanent answer.
- The response to a repeat is the withdrawal's **current state**, not a stored copy of the first response (simpler, and more useful to a client that is catching up). A stored-response design is the alternative when responses aren't derivable from state.
- Scope is per account (no clients or auth yet; with auth it becomes per client). Keys never expire here; real APIs expire them (e.g. after 24 h) so the table doesn't grow forever.

### `GET /withdrawals/:id`

The withdrawal and, with `?include=history`, its status history. `GET /accounts/:id/balance` adds `held`. The transactions list stays payments only (*Known gaps*).

### Submitter

A consumer of `withdrawal.held` (stream `WITHDRAWALS`, durable consumer `submitter`, `nats/consumers/WITHDRAWALS/submitter.json`: filter `withdrawal.held`, explicit ack, `ack_wait` 30 s, `max_deliver` 100, delays set per `nak`). It runs in its own process (`node/src/submitter/`, compose service `submitter`), on the pull loop shared with the worker (`src/consumer/consume.ts`: fetch exactly the free slots, bounded concurrency, graceful shutdown), so its scaling and failure behaviour match the worker's.

The provider call is bounded by `PROVIDER_TIMEOUT_MS` (default 5 s), which must be at most two thirds of the consumer's `ack_wait`, read from NATS at startup (so the JSON definition can't drift from the check): a call that outlived its message's lease would see the message redelivered to another instance while it is still waiting, and the withdrawal sent again with the same key at the same time. The submitter refuses to start otherwise. Just before the call it signals `working()`, so the call starts with the full lease however long the database steps before it took. The provider client (`submitter/provider.ts`) is the HTTP boundary: it builds the request only from the stored withdrawal (`Idempotency-Key` and `reference` its TypeID), so every attempt sends the identical request, and validates the answers with Zod.

For each message:
1. Log the delivery (`event_deliveries`, `consumer = 'submitter'`: one log for every consumer, decision 36). Outcomes follow the shared signal-vs-record rule (`src/consumer/messages.ts`): a done outcome is recorded, then acked; a stop or a retry is signalled first (`term`, `nak`), then recorded, so a failed write to the log can't turn a stop into a redelivery.
2. Parse `withdrawal.held`; invalid → `invalid`, term.
3. Read the withdrawal. Unknown → `invalid`, term. Not `held` (submitted or settled already, e.g. the provider's update overtook us) → `duplicate`, ack, no call. This read only saves a needless call; it is not a guard: if the withdrawal settles right after it, the call goes out anyway, the provider answers our repeated key with the same transfer, and `markSubmitted` skips.
4. Call the provider, **never inside a transaction**.
5. By outcome:

| Provider answer | Outcome kind | What the submitter does |
|---|---|---|
| `201`, or `200` for a repeat of our key | `accepted` | `held → submitted` with `provider_transfer_id` (`applied`); skipped if the withdrawal moved on meanwhile (`duplicate`). Ack |
| `422` | `refused` | `held → failed` with the reason, funds released (`held → available`). Ack. The only answer that releases funds automatically |
| timeout, network error, `5xx`, an unreadable answer | `unknown` | **The outcome is unknown**: the provider may or may not have created the transfer. `nak` with a growing delay (1 s doubling to 60 s); the redelivery asks again with **the same key**, never a new one (decision 26). The withdrawal stays `held`, funds reserved, which is right either way |
| `400` | `invalid` | Our bug (decision 35): `fatal` log with `alert: true`, term. The withdrawal stays `held` for a person; no money moves |
| `409` | `key_conflict` | Our bug: as `400` |
| `markSubmitted` throws `TransferIdMismatchError` (the provider's update stored another transfer ID) | | An invariant violation: as `400` |
| any other error (e.g. the database unavailable after an accepted call) | | `nak`; the redelivery calls again with the same key, gets the same transfer, and records it |

If `max_deliver` is exhausted, the withdrawal stays `held` (dead-letter handling is a *Known gap*); reconciliation lists it as stuck. Releasing it automatically would be wrong: the provider may have executed it (decision 26). That decision needs the provider's answer (polling it is *Out of scope*) or a person.

### `POST /provider/transfer-updates`

The provider's webhook: `{ provider_event_id, transfer_id, reference (our withdrawal TypeID), status: "executed" | "failed", reason?, occurred_at }`, a tolerant reader (`reason` required for `failed`, absent for `executed`). This is ingestion's second kind of provider notification: `ingestion/notifications.ts` split into `incoming-payments.ts` and `transfer-updates.ts`.

**`transfer_updates`** (an internal log, `bigserial` key): one row per distinct `provider_event_id` (`UNIQUE`), with `withdrawal_id` (nullable: `NULL` when the reference matches no withdrawal), `reference` as sent, `transfer_id`, `status`, `reason`, the provider's `occurred_at`, `received_at`, `notification_count` and `outcome` (what the first receipt did: `applied`, `duplicate`, `conflict`, `unmatched`). A record, not a guard: the money is decided by the withdrawal's conditional transition; the table recognises a resent update and keeps contradictions and unmatched updates on file.

One transaction (decision 29), `recordTransferUpdate()`:
1. **Record**, one statement: insert the update with `withdrawal_id` resolved from the reference, or, for the same `provider_event_id`, count a resend when its details match (`IS NOT DISTINCT FROM`, since `reason` is `NULL` for `executed`).
2. **Settle** a new, matched update: `execute(tx, id, transfer_id)` or `release(tx, id, reason, transfer_id)`. A skipped transition is then classified by a read (it only classifies; the transition decided).
3. **Set the final outcome** on the row. Conflicts and unmatched updates are **committed, not rolled back**, so they stay on file; they move no money (decision 35). Only invariant violations roll back.

| Situation | Outcome | Effect |
|---|---|---|
| New update, transition applies (from `held` or `submitted`, decision 27) | `applied` | settled: `held → external`, or funds released |
| The same `provider_event_id` resent with the same details | duplicate | `notification_count` + 1; nothing settled again |
| A second event ID for the result already recorded | `duplicate` | nothing moved |
| The withdrawal already has the **other** final status (`failed` after `executed`, or the reverse; SEPA allows neither, returns are a separate flow) | `conflict` | recorded, `error` log with `alert: true`, nothing moved |
| Another transfer ID than the one stored (`TransferIdMismatchError`, thrown after a read, so the transaction is still usable) | `conflict` | as above |
| The same `provider_event_id` with other details (the provider reused its event ID) | event conflict | nothing changed; alert |
| The reference matches no withdrawal (or isn't a `wd_` TypeID) | `unmatched` | recorded with `withdrawal_id` `NULL`; alert. Not a timing race (a withdrawal exists before it is submitted) |
| A ledger invariant violation | (rolled back) | `500`, `fatal` with `alert: true` |

**Webhook semantics** (decision 37), the real contract (`POST /provider/incoming-payments` follows it too since step 6b):

| Answer | When |
|---|---|
| `204`, no body | everything recorded or deliberately handled: applied, duplicate, conflict, event conflict, unmatched. The outcome is never echoed: the endpoint is no oracle for which withdrawals exist or their state, and providers ignore webhook bodies |
| `400` (problem details, field paths only) | a body that doesn't parse: if the bug is ours, the provider's retries deliver the update once it's fixed |
| `500` | an invariant violation (rolled back, alerted) or a transient failure: a retry helps once fixed, and keeps it visible meanwhile |

Compose sets provider-sim's `SIM_WEBHOOK_URL` to this endpoint, so a withdrawal completes end to end; since every handled case answers `204`, the sim stops resending after the first delivery, as a real provider would. Reconciliation lists `conflict` and `unmatched` updates for a person (not inconsistent books), and a withdrawal stuck in `submitted` now means a webhook that never came.

### `POST /provider/incoming-payments` (step 6b)

Slice 1's `POST /payments`, moved to the webhook contract (decisions 37–38, revising slice 1 decision 13) and under `/provider/` with the other provider webhook (`src/api/webhooks/incoming-payments.ts`). What it used to refuse is now recorded:

| Notification | Recorded | Effect |
|---|---|---|
| New, IBAN of one of our accounts | payment `created` + its `payment.created` in the outbox | as before (the worker books it) |
| The same network ID and details again (matched or unmatched) | `notification_count` + 1 | nothing else |
| New, valid IBAN matching none of our accounts | payment `unmatched` (suspense): `account_id` `NULL`, a history row, **no event, no movement** | `error` log with `alert: true` (masked IBAN) |
| The same network ID with other details | a `payment_notification_conflicts` row (the stored payment, the details received, `differing_fields`) | nothing else changed; `error` log with `alert: true` (field names, never values) |
| Refused, yet no compared field differs (our bug) | nothing | `500` |

**Suspense** is a status, `unmatched`, in `incoming_payments`: `account_id` is nullable (`CHECK (account_id IS NOT NULL OR status = 'unmatched')`), and the one idempotency key, `UNIQUE (network, network_transaction_id)`, keeps covering every notification. An unmatched payment has arrived at the bank but matches none of our accounts: recorded (money can't be refused over HTTP), booking nothing, publishing no event. Resolving it (matching it to an account, or returning it) is a manual process, out of scope; a provider retry with the same details is a duplicate of the suspense record even if the IBAN has gained an account since: resolution is never automatic. `unmatched` is outside the payment lifecycle (no transition into or out of it in this slice); in code a matched `Payment` keeps a non-null account and a `BookedStatus`, and an `UnmatchedPayment` is its own shape. Reconciliation reports suspense (count, total, oldest age, the payments) in whole-database runs, and payment notification conflicts (oldest first); neither makes the books inconsistent, and an unmatched payment with a movement would be a mismatch.

**Webhook semantics:**

| Answer | When |
|---|---|
| `204`, no body | created, duplicate, unmatched, conflict: the outcome is never echoed (no oracle for which accounts or payments exist) |
| `400` (problem details, field paths only) | a body that can't be used: malformed, oversized, not JSON, or failing validation, an invalid IBAN included (if our validation is the problem, e.g. the unverified SEPA country list, the provider's retries deliver it once fixed). The provider webhooks answer no other 4xx: Fastify's own `413` and `415` become `400` under `/provider/` |
| `500` | our inconsistency, or a transient failure: a retry helps once fixed |

### Fake provider (`provider-sim`)

A small HTTP service (decision 31; `node/src/provider-sim/`), run by compose (`provider-sim`, same image, port 4000), standing in for the BaaS. State is an in-memory map keyed by `Idempotency-Key`: a restart forgets every transfer (*Known gaps*).

**`POST /transfers`**, header `Idempotency-Key` (the submitter sends the withdrawal's TypeID). Body: `{ amount_minor, currency: "EUR", creditor_iban, creditor_name, remittance_info?, reference }` (`reference`: our withdrawal TypeID, at most 35 characters as a SEPA end-to-end ID, echoed back in updates). Validated like a real SEPA provider (IBAN through `parseIban`, the SEPA text rules): invalid → `400` listing each problem by path and message (never the input values), so the submitter's logs show why.
- A new key: the transfer is created, `201 { transfer_id: "tr_…", status: "accepted" }`, and its result is scheduled.
- The same key and the same body: `200` with the same transfer; nothing new is created or scheduled.
- The same key with another body: `409`, as real providers answer. Our submitter must never cause one: it always resends the same request.

**Results by webhook:** `SIM_EXECUTION_DELAY_MS` (default 2000) after creation, `POST` to `SIM_WEBHOOK_URL`: `{ provider_event_id, transfer_id, reference, status: "executed" | "failed", reason?, occurred_at }` (`provider_event_id` unique per update; a duplicate delivery repeats it). Retried until a `2xx` (each request with a timeout), 1 s doubling to 30 s, giving up after `SIM_WEBHOOK_MAX_ATTEMPTS` (default 20) with an `error` log: real providers give up eventually too, which is what reconciliation's stuck-`submitted` check is for. **With `SIM_WEBHOOK_URL` unset, results are logged, not sent** (compose leaves it unset until the webhook endpoint exists, step 6).

**Failure modes** (decision 34): deterministic triggers at the start of `remittance_info`, valid SEPA basic text so they pass our API's validation:

| `remittance_info` starts with | Behaviour |
|---|---|
| `SIM REFUSE` | `422 { reason }` at submission; no transfer created. Permanent: the refusal is remembered per key, so the same request is refused again (a random rate isn't re-rolled) and another body with the key is a `409` |
| `SIM ERROR` | `503` without creating the transfer, the first time only for that key; the retry succeeds |
| `SIM SLOW` | creates the transfer, then answers after `SIM_SLOW_DELAY_MS` (default 10 s, beyond the submitter's timeout): the unknown-outcome case. A retry meanwhile gets `200` at once |
| `SIM FAIL` | accepted (`201`); the result is `failed` with a reason |
| `SIM DUPLICATE` | the result is delivered twice, with the same `provider_event_id` |
| `SIM EARLY` | one delivery attempt is made before the submission is answered `201`: the race of decision 27. If that attempt fails, the retries carry on in the background, so a failing webhook doesn't hold the response |

Plus optional random rates for chaos runs, `SIM_REFUSE_RATE`, `SIM_ERROR_RATE`, `SIM_SLOW_RATE`, `SIM_FAIL_RATE`, `SIM_DUPLICATE_RATE`, `SIM_EARLY_RATE` (default 0, off). A trigger wins over the rates. Compose sets no rates: the demo should mostly succeed, and tests and the demo script choose failures by trigger.

## Reconciliation

Extended, same three views:

```text
pending_in == sum of payments in (received, under_review, approved, rejected)
available  == sum of credited payments − sum of withdrawals in (held, submitted, executed)
held       == sum of withdrawals in (held, submitted)

each bucket == net of balance_movements into/out of it
```

Per withdrawal, movements must match status: `held`, `submitted` exactly `hold`; `executed` `hold` and `execute`; `failed` `hold` and `release`; on its own account, for its own amount.

Also reported:
- withdrawals stuck in `held` or `submitted` beyond the threshold (funds reserved, outcome unknown);
- **outbox:** events unpublished beyond the threshold, and the highest `attempts` (a relay that is down, or an event the stream keeps refusing);
- payments stuck in `created` now say which side stalled: their `payment.created` event is still unpublished (the relay) or published but not processed (the worker). Every `created` payment has its outbox row, written in the same transaction, so a missing one is reported as a bug. Only unpublished events beyond the threshold make `--fail-on-stuck` fail; like stuck payments, outbox problems don't make the books inconsistent.

## Known gaps (deliberate)

Slice 1's gaps stand, except the commit-then-publish gap (closed by the outbox). New:
- **Outbox growth:** published rows are kept; a pruning job (or partitioning by month) is the evolution.
- **No backfill from slice 1:** the outbox migration creates no rows for existing payments. A slice 1 payment left in `created` (its publish failed) has no outbox row, and a duplicate notification no longer re-announces it, so it would stay there; reconciliation reports it as `missing`. A real upgrade from slice 1 would need a one-off backfill of `payment.created` rows for such payments, built by the application's event builder. Not done here: there is no slice 1 deployment, and the development database has none.
- **Suspense is a status, not an account.** In production an unmatched payment is booked into a suspense ledger account (bank -> suspense), so the books explain the bank balance (cash = customer balances + suspense + treasury/internal), and resolving it posts suspense -> customer or suspense -> bank (returned). Flows are also kept apart: notifications for known treasury or internal accounts are routed (or excluded) by a configured list rather than alerted as unknown, and customer payments, treasury flows and suspense live in separate tables, which keeps their workflows apart and makes role-based access simple. Idempotency then can't live in any one of those tables: an intake table (an inbox: one row per notification, the idempotency key and the raw payload) decides duplicates before classification routes each notification to its flow. The demo keeps one table with an unmatched status, which preserves a single idempotency key without that layer.
- **One provider's error contract:** the submitter maps provider-sim's answers to outcomes (`422` refused, `400` and `409` our bug, everything else unknown). Real providers differ: some answer `409` while a request with the same key is still in progress (which a retry right after a timeout can hit), and that is an unknown outcome to retry, not a bug. A real integration maps each provider's answers to these outcomes, typically by the error code in the response body rather than the status alone.
- **Single scheme:** field validation (lengths, the SEPA basic character set) is SEPA-specific and partly enforced by database CHECKs. With several schemes (Faster Payments, SWIFT, …), the scheme becomes a routing decision and validation moves to per-scheme rules in code, with the database keeping only scheme-independent constraints.
- **Relay latency:** idle polling adds up to the poll interval (≤ 1 s) per event; `LISTEN/NOTIFY` is the evolution.
- **No compliance review of withdrawals** (decision 30); in reality outgoing payments are screened (sanctions, fraud) before submission.
- **Webhooks are the fast path, not the guarantee.** A real integration also polls the provider (the source of truth) and reconciles against the daily statement. For withdrawals that's a status check on withdrawals still `submitted` after a threshold. For incoming payments it's **discovery**: the provider's transaction list since a checkpoint, with an overlap window, since list order isn't commit order. Both feed the same idempotent paths (`execute` / `release`; `recordNotification`), so a polled result and a webhook for the same transfer or payment apply once, and a disagreement takes the conflict path. Not built: provider-sim would need `GET /transfers/:id` and a transactions list, plus a poller.
- **Webhook authentication:** an HMAC signature over the body with a shared secret, checked before parsing; an unsigned or wrongly signed request gets a bare `401`. The precondition for any of this endpoint's answers.
- **Inbox:** storing every raw payload first, answering 2xx and processing separately: the inbound mirror of the outbox. It suits heavy, locking or waiting processing, and keeps raw payloads for audit (including unparseable ones); with polling in place, a missed webhook can't strand anything, so it isn't needed for correctness. It doesn't replace idempotency: an inbox needs its own dedupe key, and processing keeps its conditional transitions.
- **No cancellation**, and **no returns after execution** (SEPA R-transactions).
- **Idempotency keys never expire.**
- **The transactions list shows payments only;** withdrawals are read individually.
- **provider-sim forgets transfers on restart:** its idempotency is in memory. Real provider idempotency is durable (and usually time-limited).

## Decisions

Numbering continues from slice 1.

22. **Transactional outbox:** events are stored in `outbox` in the same transaction as the state change they announce; a relay publishes them (at least once, no ordering guarantee); the outbox row's ID is the `event_id`. Supersedes slice 1 decision 18 (publish failure handling) and the re-publish-on-duplicate behaviour.
23. **Relay leases:** claimed with `FOR UPDATE SKIP LOCKED` in a short transaction, published outside it, marked after the stream's acknowledgement; several relays may run.
24. **Withdrawal idempotency:** required `Idempotency-Key`, `UNIQUE (account_id, idempotency_key)` on the withdrawal itself; repeats compared field by field (no hash, as decision 16); a repeat returns the withdrawal's current state. **Only a successful request consumes a key:** failures (including insufficient funds and our own `5xx`) store nothing, so a retry with the same key is evaluated afresh. Rationale: providers that cache responses per key, failures included, turn a transient fault on their side (a cached `500`) into a permanent one for the sender, whose only way out is a new key, which defeats the key. Stripe-style "the key records the first outcome" was the alternative.
25. **Holds are synchronous:** `POST /withdrawals` reserves the funds (`move(available → held)`) in its own transaction, so the client learns at once whether the withdrawal is accepted (`201`) or refused for insufficient funds (`422`), and the answer is atomic with the reservation: the balance CHECK is the insufficient-funds check (no check-then-act). This is the banking contract: a transfer is accepted or refused when it is requested. (An exchange such as Kraken has no such need: withdrawals to an external account are infrequent and slow anyway, with checks, cool-off periods and email confirmation, so an asynchronous answer costs the client nothing. If this system gained such checks, they would be states between `held` and `submitted`, after the hold; see decision 30.) **Revises slice 1 decision 7** ("the API never changes balances"): balances change only through `ledger/` posting functions and `move()`, and the API may call a posting function inside its request transaction when the response depends on the outcome. Incoming payments are unchanged: the provider only needs to hear that its notification was recorded, not the booking's outcome, so booking stays in the worker. Insufficient funds stores nothing and leaves the key free (decision 24).
26. **Unknown outcomes are retried with the same key**, never resolved by guessing: a withdrawal whose submission outcome is unknown stays `held` until the provider answers.
27. **Provider results may arrive first:** `held → executed | failed` are legal, so the webhook never depends on the submitter's progress.
28. **Outbox rows are kept after publishing** (`published_at` set, not deleted): the outbox doubles as a record of exactly what was published and when, which reconciliation and debugging use (e.g. which side stalled for a payment stuck in `created`), and a published event can be re-sent from its row. The partial index on unpublished rows keeps the relay's query fast as the table grows; pruning or monthly partitioning is the evolution (*Known gaps*). Deleting on publish was the alternative.
29. **Provider transfer updates are applied in the webhook's own transaction:** record the update, transition the withdrawal and post its movement together, then answer. Unlike an incoming payment there is no asynchronous decision left to make, so a worker hop would add latency and an event type for nothing. It is fast enough: a handful of single-row statements, milliseconds against a provider's webhook timeout of seconds, so well inside the window before the provider gives up and resends. If it fails (e.g. the database is unavailable), the `5xx` makes the provider resend, and the conditional transition makes the resend safe. The one thing that could slow it is contention on a hot account's balance row (see slice 1's *Scaling notes*), which the load-testing slice should measure. Extends decision 25's revision of slice 1 decision 7: the API calls a posting function in its request transaction here too. In production an event hop may well be preferred anyway, for separation of concerns: ingestion only records, posting applies, and the webhook endpoint stays independent of ledger load and contention. That is the pattern incoming payments already demonstrate, so repeating it here would show nothing new (scope principle).
30. **No compliance review of withdrawals** in this slice. In reality there would be one: outgoing payments are screened (sanctions, fraud, unusual activity) before they are sent, and it would sit between `held` and `submitted` (`held → under_review → approved → submitted`, the funds already reserved), with rejection releasing the hold. It would repeat slice 1's pseudo review without demonstrating anything new (scope principle).
31. **The fake provider is test infrastructure in the Node codebase:** `node/src/provider-sim/`, run by compose as `provider-sim` from the same image, with failure modes chosen by triggers in the remittance text or by random rates set in environment variables (decision 34). It belongs to neither implementation, so the Go stack reuses it unchanged, as it reuses `scripts/demo.sh` and the reconcile service.
32. **Outgoing text fields use the SEPA basic character set** (the EPC's basic Latin set: `a-z A-Z 0-9 / - ? : ( ) . , ' +` and space; extended sets exist only by national agreement, so they are not assumed). Requests outside it are rejected (`400` from step 3), never transliterated, so what the client sees is exactly what is sent. Enforced by CHECKs on `withdrawals.creditor_name` and `remittance_info`, and by `sepaTextSchema` (`shared/schemas.ts`) at the API, which mirrors them. Leading and trailing whitespace is trimmed first (it is almost always a slip; inner whitespace is kept), and an optional field that is empty or blank means none (`null`, the one stored spelling of none): normalisations whose result the response shows, so the client still sees exactly what is stored and sent.
33. **Client request bodies are strict; provider webhooks are tolerant readers.** `POST /accounts/:id/withdrawals` rejects unknown fields (`z.strictObject`): it is our own client asking to move money, so a misspelt optional field (`remitance_info`) must fail rather than be silently dropped. `POST /provider/incoming-payments` (formerly `POST /payments`) ignores unknown fields, because providers add fields to webhooks over time and a new field must not break ingestion.
34. **provider-sim failures are chosen deterministically by triggers in the remittance text** (as provider sandboxes use magic amounts or names), with optional random rates for chaos runs. Probabilities alone would make tests and the demo flaky; a trigger makes each failure mode a test case that always happens.
35. **A provider answer that signals our bug (a `400`, a `409`, a transfer-ID mismatch), or a ledger invariant violation while recording it, moves no money:** the message is terminated with an alert and the withdrawal stays `held` for a person. Only a definitive refusal (`422`) releases funds automatically. Releasing on a bug would guess at an outcome the provider may not share. The meaning of each answer is provider-sim's contract (a `409` is only ever our key reused with another body); a real provider's answers are mapped to these outcomes by its integration (*Known gaps*).
36. **One delivery log for every consumer**, `event_deliveries` with a `consumer` column (`worker`, `submitter`), rather than a table per consumer: the same columns and the same crash trace, and reconciliation reports duplicates and stale `in_progress` rows per consumer.
37. **Transfer updates use the real webhook contract:** `204` (no body) for everything recorded or deliberately handled (contradictions and unmatched updates recorded and alerted, moving no money; no outcome echoed, so the endpoint is no oracle); `400` only for an unusable body (Fastify's own `413` and `415` included, answered as `400` under `/provider/`); `500` when a retry can help.
38. **Status codes follow the caller:** our client's API uses conventional REST codes; provider webhooks use the webhook contract. `POST /payments` moved to the webhook contract in step 6b (revising slice 1 decision 13), as `POST /provider/incoming-payments`, recording unknown-account payments in suspense and conflicts as records, not 4xx. The code follows the same split: `src/api/` holds the client API at its top level and the provider webhooks under `src/api/webhooks/` (`transfer-updates.ts`; `POST /payments` moves there in step 6b as `incoming-payments.ts`, at `POST /provider/incoming-payments`, so every provider webhook lives under `/provider/`).
